ServerBee 把 Web 管理面板使用的能力同时通过 REST 和 WebSocket API 暴露。最权威的 schema 级参考由服务端二进制中的 OpenAPI 注解自动生成。

## Swagger UI

内置交互式文档（公开可访问，无需认证）地址：

```text
https://your-server/swagger-ui/
```

你可以在 Swagger UI 中查看请求/响应模型和认证要求，并直接向自己的部署发送测试请求。原始 OpenAPI 文档地址：

```text
https://your-server/api-docs/openapi.json
```

## 响应格式

绝大多数 JSON REST 成功响应统一包装为：

```json
{
  "data": {}
}
```

不使用该 JSON 包装的例外情况：

- `204 No Content` 空响应体（例如 `DELETE /api/widget-modules/{id}`）。
- 纯文本响应（`GET /healthz` 返回 `ok`）。
- 原始二进制或静态资源响应（`POST /api/settings/backup`、`GET /api/files/download/{transfer_id}`、`GET /api/brand/logo`、`GET /api/brand/favicon`、`GET /api/widget-modules/{id}/{asset_path}`）。

应用错误包含错误码和消息，还可能包含 `details`：

```json
{
  "error": {
    "code": "BAD_REQUEST",
    "message": "Bad request: description of what went wrong"
  }
}
```

## 认证方式

受保护的 REST 路由和 `/api/ws/*` 升级按以下优先级解析凭据（首个有效凭据生效）：`session_token` Cookie → `X-API-Key` 请求头 → `Authorization: Bearer` 请求头 → Tailscale Serve 回环身份。

### Session Cookie

Web 管理面板登录后自动使用。服务端设置名为 `session_token` 的 `HttpOnly` Cookie：

```bash
curl -X POST https://your-server/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"your-password"}' \
  -c cookies.txt

curl https://your-server/api/servers -b cookies.txt
```

### API Key

自动化场景推荐使用 API Key。Admin 可在 Settings → API Keys 创建。

```bash
curl https://your-server/api/servers \
  -H "X-API-Key: serverbee_your-api-key-here"
```

API Key 使用 `serverbee_` 前缀，创建时只显示一次。API Key 会以所属用户的身份完成认证，它是凭据，不是独立角色。请求继承所属用户当前的 Admin 或 Member 权限。只有 Admin 可以创建新的 API Key。

### Bearer Session Token

`Authorization: Bearer <session-token>` 适用于**所有**受保护的 REST 端点和 `/api/ws/*` WebSocket 升级（供 iOS 客户端和其他基于令牌的客户端使用）：

```bash
curl https://your-server/api/auth/me \
  -H "Authorization: Bearer <session-token>"
```

### Tailscale Serve 回环身份认证

当 `tailscale.auth_enabled = true`（`SERVERBEE_TAILSCALE__AUTH_ENABLED=true`）时，ServerBee 支持解析本机 `tailscale serve` 注入的 `Tailscale-User-Login` 请求头，用于浏览器 REST 请求与 `/api/ws/*` WebSocket 升级。为防止身份伪造，服务端**仅在同时满足以下条件时**信任该请求头：底层 TCP 对端严格为回环地址（`127.0.0.1` 或 `::1`），**且**请求不含 `X-Forwarded-For` 或 `Forwarded` 转发头（若 `tailscale.socket_path` 指向可达的本地 Socket，还会通过 `/localapi/v0/whois` 交叉核验）。请求同时携带有效 Session Cookie、API Key 或 Bearer Token 时优先按前者认证；持久 WebSocket 连接期间会持续重验 `auth_enabled` 与用户当前角色。详见 [Tailscale 集成](/zh/docs/tailscale#方案二tailscale-serve-回环身份认证)。

### 首次强制改密门禁

当账号标记为 `must_change_password = true` 时，除三个白名单引导端点（`GET /api/auth/me`、`POST /api/auth/onboarding`、`POST /api/auth/logout`）外，所有受保护 REST 请求均返回 `403 Forbidden` 且 `error.code = "MUST_CHANGE_PASSWORD"`。`/api/ws/*` WebSocket 升级在完成密码引导前会被直接拒绝。

普通移动端刷新会保留安装注册，并使之前的 access 和 refresh 凭据失效。登录返回稳定的 `revocation_token`，客户端跨刷新保留它，登出或清除被永久拒绝的认证凭据前，将它与 `installation_id` 发往 `/api/mobile/auth/revoke`。即使等待清理请求时发生新的登录，清理仍只使用原登录上下文。该凭据只能删除其原会话、认证凭据和注册，不能认证其他 API 或刷新会话。清理上下文会在轮换前同时捕获已保存的证明和原登录的当前 refresh secret。旧 Server 在 iOS 先升级期间替换会话，可能导致本地证明为空或已经失效。若已保存的证明被拒绝，客户端只会在删除接口尝试捕获的 refresh secret，不会改用替代登录的凭据。证明为空时，应用会在联网前保存它。撤销接口可在该秘密被消费前验证它；每次成功轮换也会在同一事务中保留被消费秘密的哈希。验证和删除与轮换串行，因此无论清理请求先于消费到达，还是在已提交的响应丢失后到达，都能撤销原会话。这些哈希仅允许删除原会话，并随其删除，不能授予普通 API 权限或重用已消费的刷新令牌。其他安装、用户和替代登录保持独立。

`/api/mobile/auth/recover` 共用登录限流，且必须只使用一种验证方式：`username` 加 `password`（启用时携带 `totp_code`）、已登录网页生成的二维码 `pairing_code`，或先前返回的 `recovery_token`。二维码及授权模式无需密码字段；混用验证方式或在二维码及授权模式携带 TOTP 会被拒绝。二维码由恢复接口一次性消费，不能再用于普通登录。二维码生成后或授权签发后账号安全状态发生变化会使其失效，首次改密要求仍然生效。每次请求包含 `expected_user_id`、`installation_id`、可选的 `expected_session_id`，以及捕获的原 access、refresh 和撤销材料。恢复不会签发登录令牌，过期材料仅用于定位旧会话，不授予普通请求权限。

响应包含 `outcome`、`user_id`、`installation_id`、可为空的 `mobile_session_id` 和 `candidates`。`ok` 或 `already_absent` 确认清理，候选列表为空。若既无已知 ID，也无可匹配材料，但仍有同账号、同安装的会话，则返回 `selection_required`，列出包括过期会话在内的设备名、会话 ID、创建及最后使用时间，不会自动选择或删除会话。用户选择原会话后，再次验证账号并携带准确的 `expected_session_id` 清理。无 ID 时仅在原账号及安装没有遗留授权状态时确认不存在。无法归属的遗留状态或超过 64 个候选返回 409，保留所有记录。恢复不会选择最新会话，也不会批量删除同一安装的所有会话。

二维码及授权响应另含仅用于清理的 `recovery_token`，密码响应省略此字段。随机授权签发后五分钟过期，仅保留在客户端内存中，Server 重启后失效。Server 最多保留 128 个授权，清理过期记录，达到上限返回 429。授权绑定原账号、安装标识和完全一致的原 access、refresh 及撤销材料，不能用于普通登录、配对、刷新或其他 API 请求。选择会话和重试时复用此授权，原凭据材料须保持一致。只能选择最初列出的候选，目标会在删除前固定，重试不能更换目标或扩大列表。终态授权在有效期内保留已定位的准确目标，丢失响应后重试仅确认该目标不存在。无 ID 的不存在授权不会确认或删除后来出现的新会话状态。重启、过期或无 ID 确认不存在后出现新状态时，须扫描新的网页二维码。

## Agent Authority 与接入

所有响应遵循统一的 `{ "data": ... }` 包装格式。Agent Authority 管理操作需要 Admin；状态与事件历史属于已认证读取端点。

### `POST /api/servers` —— Onboard Server

原子地创建 Server 配置及其初始绑定 offer。`onboarding_request_id` 必填，并按当前认证操作者隔离。使用相同 ID 和相同标准化输入重试会返回同一个 `server_id`；同一 ID 搭配不同输入会返回 `409 ONBOARDING_IDEMPOTENCY_CONFLICT`。接入时也可一并传入可选计费字段（`price`、`currency`、`billing_cycle`、`billing_start_day`、`expired_at`、`renewal`、`traffic_limit`、`traffic_limit_type`；不可同时提交 `renewal.expiry_date` 和 `expired_at`）。

```json
{
  "onboarding_request_id": "019f...",
  "name": "edge-tpe-1",
  "tags": ["production"],
  "ttl_secs": 600
}
```

首次执行返回 `replayed: false` 和 `enrollment: { id, code, code_prefix, expires_at }`。重放返回 `replayed: true`，绝不再次返回明文 `code`，并可能返回 `outstanding_offer` 元数据。

### `POST /api/agent/register` —— Claim offer

此公开 Agent 端点使用 `Authorization: Bearer <enrollment_code>` 认证，并要求 Agent 自己生成 token：

```json
{ "proposed_run_token": "<至少 32 个非空白字符>" }
```

成功后会消费 offer、只保存 run token 哈希，并返回 `{ "data": { "server_id": "..." } }`。Server 永不返回明文 run token。

### Agent Authority 状态与历史

- `GET /api/servers/{id}/agent-authority` 返回 `status`（`claimed` 或 `unclaimed`）以及当前 `outstanding_offer`（如有）。
- `GET /api/agent-authority/events?server_id={id}&limit=100` 返回不含密钥的状态转换历史。Server 删除后事件仍会保留。

### Offer 与 authority 操作

- `POST /api/servers/{id}/agent-authority/re-enrollment` 携带 `{ "mode": "graceful" | "emergency", "ttl_secs": 600 }`，为 claimed authority 开始重新接入。Graceful 保留旧 authority，emergency 立即吊销并隔离它。
- `POST /api/servers/{id}/agent-authority/offers` 携带可选的 `{ "ttl_secs": 600 }`，仅在 authority 为 unclaimed 时发出 offer。
- `POST /api/servers/{id}/agent-authority/offers/{offer_id}/replace` 精确替换当前 outstanding offer，并仅返回一次新的明文 code。
- `DELETE /api/servers/{id}/agent-authority/offers/{offer_id}` 精确吊销该 offer。
- `DELETE /api/servers/{id}/agent-authority` 吊销当前 authority 并断开 Agent，但不生成 offer。

每个 Server 同时最多一个 outstanding offer。它的终态严格为 `consumed`、`revoked`、`replaced` 或 `expired` 之一。精确 ID 替换采用 compare-and-swap，过期页面或已进入终态的 offer 返回 `409`，不能覆盖更新状态。

## WebSocket 端点

| 路径 | 认证 | 说明 |
|------|------|------|
| `/api/agent/ws` | Agent Bearer token（兼容旧 Agent 的 `?token=`） | 双向 Agent 协议（按 `type` 区分的 JSON 帧）：`SystemInfo`、`Report`、`CapabilitiesChanged`、`CapabilityDenied`、`SecurityEvent`、`PingResult`、`NetworkProbeResults`、`UnlockResults` / `IpQualitySync`、`TaskResult`、`Terminal*`、`File*`、`Docker*`、`TailscaleStatus` / `TailscaleUnavailable`、`TracerouteResult` / `TracerouteRoundUpdate`、`IpChanged`、`UpgradeProgress` / `UpgradeResult`、`BlocklistAck` / `BlocklistResetAck` 及 `Ack` / `Pong` |
| `/api/ws/servers` | Session cookie、API Key、Bearer token 或 Tailscale Serve 回环身份 | 浏览器/移动端实时服务器更新（`FullSync` 包含 `tailscale_*` 字段） |
| `/api/ws/terminal/{server_id}` | 已认证 Admin + `CAP_TERMINAL` | Web 终端代理。客户端 JSON 帧：`{"type":"input","data":"<base64>"}` 与 `{"type":"resize","rows":24,"cols":80}`；服务端 JSON 帧：`session`、`started`、`output`（base64 `data`）和 `error` |
| `/api/ws/docker/logs/{server_id}` | 已认证 Admin + `CAP_DOCKER` | 按容器流式传输 Docker 日志。服务端 JSON 帧：`{"type":"session","session_id":"..."}` 与 `{"type":"logs","entries":[...]}`；客户端 JSON 帧：`{"type":"subscribe","container_id":"...","tail":100,"follow":true}` 与 `{"type":"unsubscribe"}` |

## 常见状态码

| 状态码 | 含义 |
|--------|------|
| 200 | 成功（JSON `{ "data": ... }` 包装、二进制下载，或 `/healthz` 纯文本） |
| 204 | 无内容（空响应体，例如卸载组件模块） |
| 400 | 请求错误或操作无效 |
| 401 | 未认证 |
| 403 | 无权限：角色、capability、Agent 本地策略，或首次强制改密（`MUST_CHANGE_PASSWORD`） |
| 404 | 资源不存在、服务器离线或公开页面已禁用 |
| 408 | 请求超时（`REQUEST_TIMEOUT`） |
| 409 | 冲突，例如 slug/name 重复或过期的 enrollment offer |
| 422 | 参数校验失败（`VALIDATION_ERROR`） |
| 429 | 请求过于频繁（`TOO_MANY_REQUESTS`） |
| 500 | 服务器内部错误（`INTERNAL_ERROR`） |
| 502 | 上游网关错误（`BAD_GATEWAY`）：外部投递失败（Webhook、推送服务商、邮件） |
