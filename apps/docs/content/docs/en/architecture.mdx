This page describes ServerBee's internal architecture for developers and operators who want to understand how the system works under the hood. ServerBee follows a hub-and-spoke design: a central **Server** receives metrics from distributed **Agents** over WebSocket, stores them in SQLite, and serves a React SPA dashboard.

## Component Roles

### Server (`crates/server`)

The central hub that:

- Serves the web dashboard (React SPA embedded via `rust-embed`)
- Exposes REST API endpoints for CRUD operations
- Manages WebSocket connections from agents and browsers
- Stores all data in SQLite
- Runs background tasks (record writing, aggregation, cleanup, alerting, offline detection)
- Dispatches notifications

Its main service modules are:

| Module | Responsibility |
|--------|----------------|
| Axum Router | Routes and handles HTTP/WebSocket requests |
| AgentManager | Manages agent WebSocket connections, the live metric cache, and update broadcasting |
| AuthService | User login (argon2), session management, API key verification |
| ServerService | Server CRUD, grouping, tagging, ordering |
| RecordService | Metric writes, history queries, hourly aggregation, retention cleanup |
| AlertService | Alert rule CRUD, periodic evaluation, notification dispatch |
| NotificationService | Notification channel management and message dispatch (Webhook/Telegram/Email/Bark, plus direct manual APNs channels via `ApnsService::send_push`; Push Relay mobile notifications run through the separate `MobilePushOutbox` pipeline) |
| PingService | Ping task CRUD, task assignment, result storage |
| TaskService | Remote command dispatch, result queries |
| ConfigService | System configuration read/write (key-value store) |
| TailscaleControlService | Tailscale v2 / Headscale v1 control-plane client, fleet correlation, and `tailscaled` LocalAPI `whois` verification |
| GeoIpService | IP geolocation & ASN lookup (DB-IP Lite one-click download or MaxMind MMDB) |
| UserService | User CRUD and role management |

### Agent (`crates/agent`)

A lightweight daemon deployed on each monitored server that:

- Collects system metrics using the `sysinfo` crate
- Reports metrics to the server over WebSocket every N seconds
- Runs ping probes as instructed by the server
- Provides PTY terminal sessions for remote shell access
- Executes remote commands dispatched by the server
- Supports self-upgrade when instructed

Its main modules are:

| Module | Responsibility |
|--------|----------------|
| Collector | Periodically collects CPU, memory, disk, network, and other metrics via `sysinfo` |
| Reporter | Manages the WebSocket connection, reports metrics, handles server commands, reconnects on disconnect |
| PingManager | Runs scheduled ICMP/TCP/HTTP ping tasks dispatched by the server |
| NetworkProber | Runs scheduled network quality probes and reports aggregate results |
| Tailscale | Queries local `tailscaled` via Unix socket LocalAPI or CLI fallback for periodic and on-demand status reports |
| Terminal | Manages PTY terminal sessions and forwards terminal I/O |

### Common (`crates/common`)

A shared library crate containing the types and protocol shared between the agent and server:

- **Protocol definitions** -- `AgentMessage`, `ServerMessage`, `BrowserMessage` enums
- **Data types** -- `SystemInfo`, `SystemReport`, `GpuReport`, `PingResult`, `ServerStatus`, etc.
- **Constants** -- Protocol version, default ports, timeouts, retention periods, alert parameters

### Frontend (`apps/web`)

A React 19 single-page application, embedded into the server binary via `rust-embed` after build:

- **Routing** -- TanStack Router (file-based)
- **Data fetching** -- TanStack Query for REST, native WebSocket for real-time updates (sharing the same cache)
- **UI components** -- shadcn/ui with the base-nova theme
- **Styling** -- Tailwind CSS v4
- **Charts** -- Bklit chart primitives (visx) behind shared wrappers in `components/charts/`
- **Terminal** -- xterm.js web terminal emulator
- **Build** -- Vite 7

The built frontend is embedded into the server binary at compile time, so there is nothing to deploy separately.

## Communication Protocol

Agent reporting and control traffic uses WebSocket. Browsers use REST for initial data, history, and management operations, plus WebSocket for real-time updates. WebSocket application messages are JSON text frames; terminal I/O data is carried inside the message's `data` field, base64-encoded. The current Agent protocol version is `6`, sent in the `Welcome` message on connect.

The agent connects to `ws://<server>/api/agent/ws` and authenticates with `Authorization: Bearer <agent_token>`. The Server temporarily accepts the legacy `?token=` form so older Agents can reconnect and upgrade.

### Agent to Server (`AgentMessage`)

| Message Type | Purpose | Needs ACK |
|-------------|---------|-----------|
| `SystemInfo` | Static system information, capabilities, and temporary grants, sent on connect/reconnect | Yes |
| `CapabilitiesChanged` | Updated host capability policy, temporary grants, and change events | Yes |
| `Report` | Periodic metric report (every N seconds) | No |
| `PingResult` | Result of a ping probe | No |
| `SecurityEvent` | Host security event (SSH login, brute-force, port scan) | No |
| `TaskResult` | Output from a remote command execution | Yes |
| `TerminalOutput` / `TerminalStarted` / `TerminalError` | PTY session lifecycle and base64-encoded output | No |
| `CapabilityDenied` | Rejection of a server request blocked by agent-local capability policy | No |
| `NetworkProbeResults` | Batch results of scheduled network quality probes | No |
| `UnlockResults` | Egress IP and streaming/AI unlock probe results | No |
| `IpChanged` | Detected IPv4/IPv6 or network interface change | No |
| `TracerouteResult` / `TracerouteRoundUpdate` | Legacy completion or streamed per-round traceroute hops | No |
| `FileListResult` / `FileStatResult` / `FileReadResult` / `FileOpResult` | Sandboxed directory listing, metadata, Base64 file read, and write/delete/mkdir/move responses | No |
| `FileDownloadReady` / `FileDownloadChunk` / `FileDownloadEnd` / `FileDownloadError` | Streamed file download frames | No |
| `FileUploadAck` / `FileUploadComplete` / `FileUploadError` | Streamed file upload acknowledgements and status | No |
| `DockerInfo` / `DockerContainers` / `DockerStats` / `DockerLog` / `DockerEvent` | Docker system info, containers, stats, batched logs, and lifecycle events | No |
| `DockerUnavailable` / `DockerNetworks` / `DockerVolumes` / `DockerActionResult` / `FeaturesUpdate` | Docker daemon availability, networks, volumes, action status, and feature flags | No |
| `TailscaleStatus` / `TailscaleUnavailable` | Host `tailscaled` node summary, routes, and peers (or unavailability) | No |
| `UpgradeProgress` / `UpgradeResult` | Transactional self-upgrade stage updates and terminal failure report | Yes |
| `BlocklistAck` / `BlocklistResetAck` | Firewall nftables blocklist apply/reset acknowledgements | No |
| `Pong` | Compatibility response for JSON `ServerMessage::Ping` (heartbeats use WS-level Ping/Pong frames) | No |

### Server to Agent (`ServerMessage`)

| Message Type | Purpose |
|-------------|---------|
| `Welcome` | Sent on connect with `server_id`, `protocol_version`, `report_interval`, and capability ack flags |
| `Ack` | Acknowledges a received message (by `msg_id`) |
| `PingTasksSync` | Sync all assigned ping tasks to the agent |
| `NetworkProbeSync` | Sync scheduled network quality probe targets, interval, and packet count |
| `IpQualitySync` / `IpQualityRunNow` | Sync unlock check services/interval or trigger an immediate check |
| `Exec` | Execute a shell command on the agent |
| `TerminalOpen` / `TerminalInput` / `TerminalResize` / `TerminalClose` | PTY session lifecycle and base64 keyboard input |
| `FileList` / `FileStat` / `FileRead` / `FileWrite` / `FileDelete` / `FileMkdir` / `FileMove` | Sandboxed remote file operations |
| `FileDownloadStart` / `FileDownloadCancel` / `FileUploadStart` / `FileUploadChunk` / `FileUploadEnd` | Streamed file transfer commands |
| `DockerListContainers` / `DockerStartStats` / `DockerStopStats` / `DockerEventsStart` / `DockerEventsStop` | Docker container listing, stats polling, and event streaming |
| `DockerGetInfo` / `DockerListNetworks` / `DockerListVolumes` | Docker system info, networks, and volumes queries |
| `DockerLogsStart` / `DockerLogsStop` | Start or stop streaming logs for a container |
| `DockerContainerAction` | Execute container action (`start` / `stop` / `restart` / `remove`) |
| `TailscaleGetStatus` | Request an on-demand `tailscaled` status snapshot |
| `Traceroute` | Start an ICMP/TCP/UDP traceroute toward a target |
| `BlocklistSync` / `BlocklistAdd` / `BlocklistRemove` / `BlocklistReset` | Reconcile, update, or wipe agent nftables firewall rules |
| `Upgrade` | Instruct the agent to self-upgrade to a target version |
| `Ping` | Legacy protocol-level ping variant (the server sends WebSocket-level `Message::Ping` frames every 30s) |

### Server & Browser WebSockets (`BrowserMessage` / `BrowserClientMessage`)

Browsers obtain data through the REST API (initial load, history, and mutations) and three WebSocket endpoints:

- `ws://<server>/api/ws/servers` — **bidirectional** fleet stream: primarily server-to-browser push (`BrowserMessage`), plus upstream `BrowserClientMessage` (`DockerSubscribe`, `DockerUnsubscribe`) to toggle live Docker stats/events per server.
- `ws://<server>/api/ws/terminal/{server_id}` — interactive PTY terminal relay.
- `ws://<server>/api/ws/docker/logs/{server_id}` — live container log stream.

REST results and WebSocket messages are projected into the same live server catalog so views stay current.

| Message Type (`BrowserMessage`) | Purpose |
|-------------|---------|
| `FullSync` | Complete state of all servers and active upgrade jobs (sent on browser connect) |
| `Update` | Incremental update with latest live metrics for changed servers |
| `ServerCatalogChanged` | Signals REST server catalog invalidation (keeps private billing fields off metric frames) |
| `ServerOnline` / `ServerOffline` | Server online/offline state transitions |
| `AgentAuthorityChanged` | Enrollment offer / claim / revocation state changes |
| `CapabilitiesChanged` | Updated host capabilities and temporary grants |
| `AgentInfoUpdated` | Updated protocol or agent version metadata |
| `SecurityEvent` | Real-time host security event notification |
| `UpgradeProgress` / `UpgradeResult` | Live agent self-upgrade progress and completion status |
| `NetworkProbeUpdate` / `TracerouteUpdate` | Live network probe results and per-round traceroute hops |
| `DockerUpdate` / `DockerEvent` / `DockerAvailabilityChanged` | Docker container stats, lifecycle events, and daemon availability |
| `ServerIpChanged` | Detected agent IPv4/IPv6 or remote address change |
| `BlocklistChanged` / `FirewallApplyStateChanged` | Firewall blocklist mutations and per-server nftables apply states |
| `IpQualityUpdate` | Updated IP quality snapshot and streaming/AI unlock results |

### Handshake

```
Agent                              Server
  |                                  |
  |--- WebSocket connect + token --->|
  |                                  | verify token, look up server
  |<-- Welcome { server_id,         |
  |     protocol_version: 6,        |
  |     report_interval: 3 } -------|
  |                                  |
  |--- SystemInfo { cpu_name,       |  static info on connect/reconnect
  |     os, mem_total, ... } ------>|
  |<-- Ack { msg_id } -------------|
  |                                  |
  |--- Report (every 3s) ---------->|  periodic metric report
```

### Message Size Limits

| Limit | Maximum Size |
|-------|--------------|
| WebSocket message size | 1 MB |
| Command output | 512 KB |
| Command length | 8 KB |

### Terminal Data Transport

Terminal traffic uses the same JSON text protocol as the rest of the system, relayed through the server:

```
Browser <--JSON WebSocket--> Server <--JSON WebSocket--> Agent (PTY)
```

The raw PTY byte stream is base64-encoded into the `data` field of a JSON message, because terminal output is not UTF-8 safe.

`Browser <-> Server` messages (all JSON text):

- Browser -> Server: `{ "type": "input", "data": <base64> }`, `{ "type": "resize", "rows": <n>, "cols": <n> }`
- Server -> Browser: `{ "type": "session", "session_id": <id> }`, `{ "type": "started" }`, `{ "type": "output", "data": <base64> }`, `{ "type": "error", "error": <message> }`

`Server <-> Agent` messages reuse the agent protocol:

- Server -> Agent: `ServerMessage::TerminalOpen`, `TerminalInput` (`data` base64), `TerminalResize`, `TerminalClose`
- Agent -> Server: `AgentMessage::TerminalStarted`, `TerminalOutput` (`data` base64), `TerminalError`

## Database Design

ServerBee uses SQLite (WAL mode), managed through sea-orm. The representative tables below cover the core schema, grouped by category.

### Authentication

| Table | Purpose |
|-------|---------|
| `users` | User accounts (id, username, argon2 password hash, role, TOTP secret) |
| `sessions` | Active login sessions (SHA-256 token hash, IP, user agent, expiry) |
| `api_keys` | API key credentials (argon2-hashed key, prefix, last used) |
| `oauth_accounts` | Linked OAuth provider accounts |

### Server Management

| Table | Purpose |
|-------|---------|
| `servers` | Registered servers (token hash, system info, metadata, pricing, group assignment) |
| `server_groups` | Logical groups for organizing servers |
| `server_tags` | Tag labels attached to servers (many-to-many) |
| `configs` | Key-value configuration store (runtime settings, etc.) |

### Monitoring Data

| Table | Purpose |
|-------|---------|
| `records` | Raw metric records, one row per server per minute (composite index server_id + time) |
| `records_hourly` | Hourly aggregated metric averages (same shape as `records`) |
| `gpu_records` | Per-GPU device metrics (device index, name, memory, utilization, temp) |
| `ping_records` | Ping probe results (latency, success, error; composite index task_id + server_id + time) |
| `ping_tasks` | Ping task definitions (probe type, target, interval, assigned servers) |
| `traffic_hourly` | Hourly traffic byte counters (in/out) per server |
| `traffic_daily` | Daily traffic byte counters (in/out) per server |
| `traffic_state` | Last-known cumulative traffic counters for delta calculation |
| `docker_events` | Docker container lifecycle events (start/stop/die/create) |

### Alerting & Operations

| Table | Purpose |
|-------|---------|
| `alert_rules` | Alert rule definitions (conditions, cover type, trigger mode) |
| `alert_states` | Current alert state per rule/server pair (composite unique index rule_id + server_id) |
| `notifications` | Notification channel configs (webhook, telegram, bark, email, apns) |
| `notification_groups` | Groups of notification channels |
| `tasks` | Remote command tasks (command, target servers, created by) |
| `task_results` | Command execution results (output, exit code) |
| `audit_logs` | User action audit trail (action, detail, IP) |

All tables use UTC timestamps. IDs are UUIDs (string type) for most entities, and auto-incrementing integers for high-volume records.

### SQLite Configuration

- **WAL mode** -- `PRAGMA journal_mode=WAL` runs on every pooled connection to improve concurrent read performance.
- **Synchronous mode** -- `PRAGMA synchronous=NORMAL`.
- **Foreign keys** -- `PRAGMA foreign_keys=ON` enforces referential integrity.
- **Busy timeout** -- 5000ms; writers wait automatically on write contention.
- **Temp store & cache** -- `PRAGMA temp_store=MEMORY` and `PRAGMA cache_size=-16000` (~16 MB page cache per connection).
- **Connection pool** -- Up to 10 connections by default, primarily for concurrent reads.

## Background Tasks

The server spawns long-running background workers via `tokio::spawn` at startup (plus `BrowserFrameCoalescer` inside `AppState`):

| Task | Interval | Description |
|------|----------|-------------|
| **RecordWriter** | 60s | Flushes the latest cached agent reports from memory to the `records` table |
| **AlertEvaluator** | 60s | Advances opt-in billing renewals (`renewal::advance_all`), evaluates all enabled alert rules, and dispatches notifications |
| **OfflineChecker** | 10s | Scans agent connection state and triggers offline events/alerts for agents with no heartbeat in 30 seconds |
| **Aggregator** | 1 hour | Computes hourly rollups from raw `records` into `records_hourly` for long-term storage |
| **Cleanup** | 1 hour (60s startup delay) | Deletes records, GPU data, ping/probe records, security/IP-quality events, and audit logs older than their retention periods |
| **SessionCleaner** | 1 hour | Removes expired user sessions, TOTP challenges, and stale rate-limit windows |
| **TaskScheduler** | Cron-driven | `task_scheduler::restore_and_start` restores and dispatches scheduled remote command tasks |
| **ServiceMonitorChecker** | 10s (5s startup delay) | Dispatches due SSL, DNS, HTTP keyword, TCP, and WHOIS checks |
| **UpgradeTimeout** | 10s | Marks timed-out agent upgrade jobs and cleans up old finished upgrade records |
| **MobilePushOutbox** | Continuous | Delivers queued mobile push notifications asynchronously through Push Relay |
| **SecurityRecovery** | Continuous | `security_service.start_recovery()` reconciles interrupted security/firewall operations |
| **BrowserFrameCoalescer** | Continuous (`AppState`) | Coalesces and broadcasts real-time metric updates to connected browsers |

Event-driven pushes such as `PingTasksSync` are dispatched immediately on configuration changes rather than by a polling loop.

**Scheduling notes:**

- Hourly tasks: `Cleanup` sleeps 60 seconds before its first tick so `Aggregator` runs ahead of `Cleanup` on each hourly cycle.
- Minute tasks: `RecordWriter` and `AlertEvaluator` run on independent 60-second intervals with no explicit barrier or offset between them.

## Security Model

### Authentication Paths

User-facing REST and WebSocket requests resolve a user from a session cookie, API key, Bearer session token, or (when `tailscale.auth_enabled` is active on a strict loopback peer without proxy forwarding headers) `Tailscale-User-Login`. The authorization check then uses that user's current role. Agent WebSocket connections use a separate per-Agent run token.

```
Request arrives
  +-- Cookie: session_token=xxx         --> Session auth (browser)
  +-- Header: X-API-Key: serverbee_xxx  --> API key auth (automation)
  +-- Header: Authorization: Bearer xxx  --> Session auth (mobile)
  +-- Header: Tailscale-User-Login      --> Loopback Tailscale Serve auth (optional)

Agent WebSocket connects
  +-- Header: Authorization: Bearer xxx  --> Agent run-token auth
  +-- Query: ?token=xxx                  --> Legacy Agent compatibility only
```

#### Session-based (browser)

- User logs in with username/password, verified with argon2.
- A random 32-byte token (base64url-encoded) is generated.
- The token's SHA-256 hash is stored in the `sessions` table (never the plaintext token), and the raw token is sent in an HttpOnly + SameSite=Strict cookie.
- Sliding expiry: each valid request extends `expires_at` (default TTL 24 hours).

#### API Key (automation)

- Admin users can create named API keys for programmatic access.
- Key format: `serverbee_` + 32 random bytes (base64url).
- Keys are hashed with argon2; an 8-character plaintext prefix is stored for identification.
- On verification, the prefix narrows the lookup, then argon2 verifies the key.
- A key authenticates as its owning user and inherits that user's current `admin` or `member` role. An API key is a credential type, not a third role.

#### Agent Token (agents)

- An enrollment offer is bound to one Server, single-use, and short-lived. Its lifecycle is owned by the Agent Authority module.
- Before claiming an offer, the Agent generates and persists its run token, then submits it as `proposed_run_token`. The Server never generates or returns that token.
- The run token is hashed with argon2 and stored in the `servers` table; only the Agent retains the plaintext.
- Agents authenticate with the `Authorization: Bearer <agent_token>` header. Current Agents never place the raw token in the URI; query-token authentication remains a deprecated compatibility path for older releases.
- WebSocket admission has two stages: preflight validation before the HTTP upgrade, then final validation while holding the Server lifecycle lock. Authority transitions and frame dispatch share that lock, so a revoked or replaced connection cannot race through after fencing.
- Every authority/offer transition appends a secret-free event. Events retain a snapshot of the Server identity and survive Server deletion.

### Role-Based Access

Two user roles exist: `admin` (full access) and `member` (read-only dashboard access). Session cookies, Bearer session tokens, and API keys are credentials for one of these users; they do not define additional roles.

Browser-facing WebSockets re-check the persisted session or API key and the user's role while connected. Logout, API-key deletion, password-reset session revocation, account deletion, or a role change closes the existing socket within two seconds instead of preserving handshake-time privileges.

| Resource | Admin user | Member user | Agent |
|----------|------------|-------------|-------|
| Server list/detail | Yes | Yes (limited) | - |
| Server create/update/delete | Yes | No | - |
| Alert rule management | Yes | No | - |
| Notification config | Yes | No | - |
| User management | Yes | No | - |
| System settings | Yes | No | - |
| Real-time server updates | Yes | Yes | - |
| File Manager | Yes | No | - |
| Web terminal | Yes | No | - |
| Remote commands | Yes | No | - |
| Metric reporting | - | - | Yes |

### OAuth

OAuth login is supported for GitHub and Google. The `allow_registration` flag controls whether new users are automatically created on first OAuth login.

### Rate Limiting

Uses in-memory `DashMap`-backed per-IP counters on `AppState`. The `login` and `register` buckets are checked inline in route handlers, while the `/api/status/*` `public` bucket is enforced via Axum route middleware (`from_fn_with_state`):

| Endpoint | Limit |
|----------|-------|
| `POST /api/auth/login`, `POST /api/mobile/auth/login`, `POST /api/mobile/auth/recover` | 5 requests per IP within a 15-minute window (shared `login` bucket, counted before credential verification) |
| `POST /api/agent/register` | 10 attempts per IP within a 15-minute window |
| `GET /api/status/*` | 60 requests per IP within a 60-second window |

Exceeding a limit returns `429 Too Many Requests`. Admins can inspect and clear active windows from Settings → Rate limits.

### TOTP

Users can enable TOTP-based two-factor authentication for additional security.
