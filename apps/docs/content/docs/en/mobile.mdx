ServerBee provides a native iOS companion app that brings server monitoring to your phone: real-time metrics, alert history, and server management on the go. Verified notification setup and final scheduled-task outcome notifications are available, with successes requiring opt-in. Encrypted alert triggers and recoveries are available through confirmed mobile subscriptions. Security delivery remains under development.

## Availability

This repository does not currently publish an installable iOS artifact or an App Store/TestFlight acquisition link. The guide below applies to a build you receive from your ServerBee operator or build from source. To build it yourself, install Xcode and XcodeGen, then run:

```bash
cd apps/ios
xcodegen generate
open ServerBee.xcodeproj
```

Source builds require your Apple development team. The official-app design keeps APNs credentials at a dedicated publisher-operated Relay; official-app users and self-hosted Server operators do not need the publisher's keys. This repository does not yet distribute that signed app. A local build does not prove App Attest admission or APNs delivery.

## Features

- **QR Code Pairing** -- Scan a QR code from the web app to authenticate instantly, no manual token entry required
- **Verified Notification Setup** -- Explicit permission and subscription setup with App Attest verification; final task outcomes for administrator owners, with success opt-in; encrypted alert triggers and recoveries without a notification group
- **Real-time Metrics** -- Live server status, CPU, memory, disk, and network metrics streamed via WebSocket
- **Alert History** -- View recent alerts and their status (triggered/resolved) with detailed information
- **Secure Authentication** -- Bearer token-based auth with automatic refresh (15-min access token, 30-day refresh token)

## Requirements

- iOS 17.0 or later
- A ServerBee server instance (v0.8.0+) with mobile auth enabled
- For verified notification setup: a configured HTTPS Push Relay and a correctly signed, App Attest-capable physical device

## Pairing Your Device

### 1. Enable Mobile Auth (Server-side)

Mobile authentication is enabled by default in v0.8.0+. No additional server configuration is required unless you want to adjust token TTLs.

Optional configuration in `server.toml`:

```toml
[mobile]
access_ttl = 900      # Access token lifetime in seconds (default: 15 minutes)
refresh_ttl = 2592000 # Refresh token lifetime in seconds (default: 30 days)
```

### 2. Start Pairing from Web App

1. Log in to your ServerBee web app
2. Go to **Settings** → **Mobile Devices**
3. Click **Pair New Device**
4. A QR code will be displayed with a 5-minute expiry timer

### 3. Scan with iOS App

1. Open the ServerBee iOS app
2. Tap **Scan QR Code** on the welcome screen
3. Point your camera at the QR code displayed in the web app
4. The app will automatically authenticate and show your server list

## Managing Paired Devices

### View Paired Devices

In the web app, go to **Settings** → **Mobile Devices** to see all paired iOS devices:

- Device name (e.g., "iPhone 15 Pro")
- Paired date and time
- Last active timestamp

### Revoke Access

To remove a device's access:

1. In the **Mobile Devices** list, find the device you want to remove
2. Click the **Revoke** button
3. Confirm the action

The device will be immediately logged out and all its tokens invalidated.

## Verified Notification Setup

Signing in does not request notification permission. Open **Settings → Notifications**, choose subscriptions, then tap **Enable notifications**. The Server confirms the saved preferences before iOS asks for permission. Security and task subscriptions require an administrator. Successful-task delivery is disabled by default; eligible task recipients can opt in.

The notification page uses permissions confirmed by the Server, even if the cached login role is outdated. After an administrator is demoted, saving subscriptions or disabling notifications clears unavailable security and task categories. Failed saves do not replace the confirmed preferences.

A failed subscription save remains visible after returning to the app, reconnecting or recovering registration. The page retains the unconfirmed choices until a successful save or a newer settings revision from the Server confirms the submitted permitted preferences. A successful registration alone does not confirm those choices.

The screen reports system permission and Server registration independently. Failed saves retain the previous confirmed preferences and show an error. **Retry notification setup** retries verification, and **Open notification settings** opens iOS permission settings. Unsupported or rejected App Attest leaves push unavailable while login and monitoring continue to work. Setup is reconciled on launch, foreground entry and restored connectivity without prompting during sign-in.

**Enable Alerts and recoveries to receive alert transitions.** Use **Send test notification** to test only this authenticated installation. The Server encrypts the message, the Relay sends it through the verified device grant, and the Notification Service Extension decrypts and localizes it. The screen reports provider acceptance separately from device presentation, which must be observed on a real device. Tapping a valid test opens the current account; old account/deployment or invalid payloads cannot navigate. Final task failures and opted-in successes use the same encrypted pipeline. Administrators can also enable security-rule notifications.

Tests first enter a durable encrypted Server outbox. **Pending** means queued locally, **Retryable** means provider acceptance is unconfirmed and another attempt is scheduled, **Accepted** is an APNs provider receipt, **Permanent** stops retries, and **Expired** ends the test 30 minutes after its original creation. Retries and Server restarts never extend that deadline. The screen refreshes the current test status; retrying a lost response retains the same logical test identity. Delivery can be duplicated after an ambiguous network failure, so neither acceptance nor retry promises exactly-once display.

Before every attempt the Server checks the account, current role, mobile session, subscription, grant expiry and registration revision. Disabling delivery, logout, device/account revocation, session expiry or a registration replacement stops later eligible attempts. Already in-flight or accepted APNs notifications cannot be retracted. Queue records contain ciphertext, not another plaintext notification history. Terminal ciphertext is erased; secret-free delivery receipts remain to prevent duplicate enqueueing from restarting the expiry window.

### Alert Triggers and Recoveries

The Server queues encrypted notifications for each currently eligible subscribed installation, independently of external notification groups. Enabled rules retain their existing coverage, maintenance, trigger-mode and suppression behavior. Recovery follows the existing evaluator's transition behavior, including during maintenance. Unsubscribing before dispatch stops later eligible sends for that installation. External channels retain their own groups; migrated installations stay excluded from legacy APNs delivery.

Taps wait for authentication restoration and validate the current deployment, account and installation. The alert target includes the rule, Server, event dimension and trigger cycle. A deleted alert or overwritten cycle shows **Alert not found** with **Back to alerts**, rather than opening a newer cycle. The extension localizes trigger/recovery text in English or Simplified Chinese; decryption failure shows generic text without a navigation target.

Queued delivery and extension presentation expire 30 minutes after creation. Tapping a notification already shown in Notification Center after that deadline still authenticates its exact target and requests current Server detail. Expiry does not authorize access: a changed login is rejected, and a deleted or unavailable alert uses the same safe fallback.

### Final Task Failures

Enable **Final task failures** as an administrator. A manually started scheduled task notifies its initiator; an automatic run notifies its creator, independently of other subscribed administrators. Each eligible installation receives one logical summary after all targets finish their final attempts. Intermediate failures stay silent; a successful final retry follows the success opt-in policy. Final failed exits, timeouts, offline targets and execution denials are counted separately, including runs with no executable targets. Interrupted or incomplete runs are never treated as successful. After all final attempts drain, the Server durably records their summary before queue admission. A failed admission or Server restart automatically retries that recorded summary with the original run identity and 30-minute delivery window, checking current access and subscriptions again. Intermediate retry rows are not a completion signal.

Summaries contain counts and task/run identifiers, never task names, commands or command output. Tapping opens authenticated results filtered to that exact run, including when an already displayed notification is tapped after its delivery window. Expired new deliveries still render a generic fallback; a tap retains the authenticated target and checks current Server access. Deleted tasks, unavailable runs or lost access show a dismissible fallback; old account/deployment notifications cannot navigate. Current administrator access, ownership and subscription are checked again before queued delivery. No notification group is required. Successful-run notifications require a separate opt-in.

### Successful Task Runs

**Successful task runs** is disabled by default and appears only when the Server confirms current task access. Enable it and save subscriptions to receive one encrypted summary for a complete run in which every target ultimately succeeded, including success after a retry. This choice is independent of **Final task failures**; a mixed or failed run follows only the failure subscription and never emits a duplicate success summary. Interrupted, cancelled or incomplete runs cannot produce a success summary.

Successful summaries use the same initiator/creator ownership, per-installation eligibility, run identity, authenticated navigation and 30-minute window as failures. They contain only counts and identifiers, never task names, commands or output. Failed saves retain the previous confirmed preference and keep the unconfirmed choice and error visible. Opting out or losing administrator access cancels pending eligible success delivery when the queue rechecks access before sending; in-flight or accepted APNs requests cannot be retracted.

### Security Rule Notifications

Administrators can enable **Security rule matches** and save the Server-confirmed subscription. Members cannot subscribe. A raw detection alone never sends a mobile notification: an enabled SSH new-IP login, brute-force or port-scan rule must admit it. Thresholds, username/CIDR exclusions, Server coverage, maintenance and the existing sliding deduplication window apply. A matching event produces one logical security notification per eligible installation, even if multiple rules match, without requiring a notification group. External channels keep their configured groups.

An authorized Agent WebSocket transfers each original detection to a Server-owned recovery queue without waiting for storage retries inside its message or lifecycle lock. Before the first successful raw write, this retention is in memory and cannot survive process death. Connection replacement or closure does not discard accepted work, but authority transfer/revocation or capability removal cancels raw writes and unresolved rule admissions that are no longer authorized. The Server persists the original security event, authority binding, maintenance decision at the original event time, and recovery marker, then commits the rule cooldown together with a durable recipient intent. Maintenance lookup failures preserve raw history and browser updates while leaving rule admission unresolved; recovery never treats a failed lookup as permission. Once stored, the maintenance decision survives delayed recovery and restart across a window beginning or ending. Originals sharing a rule deduplication key are admitted in original time order across memory retention, missing maintenance snapshots and database reopen; an unresolved older event holds only that key, while other ready keys and installations continue. Rule cooldown remains monotonic in persistent storage. Only then does it encrypt and queue all eligible installations in one transaction. A queue write failure preserves raw history, browser updates, firewall actions and external notifications, leaves no partial fan-out, and retries the original intent automatically after recovery or a Server restart. Recipient ownership, session and registration revision are fixed by the intent and rechecked before queueing; replacement registrations cannot inherit an older intent. Security notifications expire 30 minutes after the event is recorded. Before each attempt, the Server rechecks the current administrator role, security subscription and mobile session. A queued notification stops after a role downgrade or subscription change. Multiple devices are evaluated independently. Retries after an ambiguous network failure can still lead to duplicate device presentation.

The Notification Service Extension localizes the admitted event type. Tapping opens the corresponding Server security feed and event detail after verifying the deployment/account, current administrator role and resource identities. A deleted, unavailable or unauthorized target shows a dismissible unavailable screen; an old account or deployment payload cannot navigate. Local tests do not establish genuine App Attest admission or foreground/background/terminated APNs delivery.

### Privacy Boundary

The Server owns account/session authorization and recipient selection. The Relay sees APNs tokens, source IPs, timing, request sizes, environment, grant identifiers and encrypted content. It must never receive content keys or plaintext notification content. Users see this explanation before requesting permission.

Server registration status includes Relay grant inspection. A revoked or unreachable grant is unconfirmed even when its saved expiry is in the future. If Relay renewal succeeds but the Server save fails, the app keeps the pending grant in Keychain and retries confirmation after foreground entry or restart. App Attest keys belong to one paired login; a replacement login receives a separate key.

### Server and Relay Configuration

Set `[push_relay].url` or `SERVERBEE_PUSH_RELAY__URL` to the dedicated HTTPS Relay. No notification group or legacy APNs channel is required. Verified migration removes this account's old token and permanently excludes that installation/account from legacy direct-APNs fan-out, even after disabling or unregistering. Other installations retain their legacy channels. Existing external channels continue to use their own configuration.

Relay operators use Bun and OpenSSL 3, persistent SQLite, an App Attest root certificate pinned with `APP_ATTEST_ROOT_CA` and `APP_ATTEST_ROOT_SHA256`, the app identity in `APP_ATTEST_APP_ID`, approved `CFBundleVersion` values in `APP_ATTEST_BUNDLE_VERSIONS`, and `APNS_ENVIRONMENTS=sandbox,production` to admit development and distribution devices on one Relay URL and database. A single-environment deployment can use `APNS_ENVIRONMENT`. `RELAY_DATABASE` and `RELAY_PORT` select local state and listener. The Relay binds loopback and requires a TLS reverse proxy with admission limits. Challenge and assertion counters persist across restarts. There is no public send endpoint or unverified fallback.

APNs transport uses publisher-only signing inputs `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY` and `APNS_TOPIC`. `APNS_PRIVATE_KEY` is the path to a private PEM file, and `APNS_TOPIC` is the app bundle identifier. These credentials must remain outside the app, Server and repository. See the repository's `apps/push-relay/README.md` for isolated configuration, signing checks and live acceptance. Do not point tests at Heeler's Relay.

## Security Considerations

- **Token Rotation**: Refresh tokens are rotated on every use (single-use). Consumed refresh tokens cannot authenticate APIs or refresh again. Their retained hashes can only revoke the original session, supporting cleanup after a staged app upgrade or a lost rotation response.
- **Fixed Expiry**: Access tokens have fixed 15-minute expiry (no sliding renewal) to limit exposure if stolen
- **Secure Storage**: Tokens are stored in iOS Keychain with appropriate accessibility levels
- **Session Expiry**: Expired access-token sessions are removed hourly. Paired-device refresh sessions are not deleted by that task: the device list hides them after expiry, refresh rotation preserves their identity and installation registration, and logout or revoke deletes them together with their retained revocation-proof hashes.

## Troubleshooting

### QR Code Won't Scan

- Ensure the QR code is displayed clearly on your screen
- Check that the QR code hasn't expired (5-minute timeout)
- Try generating a new QR code from the web app

### Notification Setup Fails

- Check the configured Relay URL and its HTTPS trust chain.
- Check Settings → Notifications for permission, verification and save errors.
- Confirm the paired device has not been revoked and the session has not expired.
- App Attest requires a supported physical device and matching signing capabilities. Simulator success is not device verification.
- Use the final HTTPS Server URL before registering a content key. Server requests reject redirects; failed setup can be retried at the configured endpoint.
- Check signing for the app-private credential group and the app/extension shared content-key group. Decryption failures show generic text.
- Enable **Alerts and recoveries**, or **Final task failures** and optional **Successful task runs** as an administrator. Security delivery remains under development.

### Authentication Failures

- If the app shows "Session Expired", it will automatically refresh the token
- If refresh fails, you'll need to re-pair using a new QR code
- Check that your server time is correctly synced (NTP)

## Technical Details

### Authentication Flow

1. **Login/QR Pair**: POST `/api/mobile/auth/login` or QR pair endpoint → returns access_token + refresh_token
2. **API Requests**: Include `Authorization: Bearer {access_token}` header
3. **Token Refresh**: On 401, POST `/api/mobile/auth/refresh` with refresh_token → new token pair
4. **Logout**: POST `/api/mobile/auth/logout` revokes all tokens for the device

### WebSocket Connection

The iOS app maintains a WebSocket connection for real-time updates:
- Connection URL: `wss://your-server/api/ws/servers`
- Authentication via `Authorization: Bearer` header during handshake
- Automatic reconnection with exponential backoff
- Connection auto-closes when access token expires (reconnect triggers refresh)
