ServerBee includes a flexible alerting system that evaluates metric thresholds and security events, then sends notifications through multiple channels when conditions are met.

## How Alerts Work

A background task evaluates all enabled polling rules every 60 seconds:

1. Resolve which servers each rule covers.
2. Check whether the rule's conditions are met for each covered server.
3. Send a notification (`event: "triggered"`) when a rule triggers (subject to debounce).
4. Clear the alert state and send a recovery notification (`event: "resolved"`) when a previously triggered rule recovers.

Alert state is persisted in the database and survives server restarts. Event-driven rules (`ip_changed`, `ssh_new_ip_login`, `ssh_brute_force_detected`, `port_scan_detected`, `capability_grant_detected`) are evaluated when an agent reports the event, not on the 60-second cycle.

## Creating Alert Rules

An alert rule consists of:

- **Name** -- A descriptive label.
- **Rules** -- One or more condition items. For polling metric rules, all conditions must be true simultaneously (AND logic). Security-event items (`ssh_new_ip_login`, `ssh_brute_force_detected`, `port_scan_detected`) cannot be mixed with non-security items, and at most one security item is allowed per rule.
- **Trigger mode** -- `always` (repeat with 5-minute debounce) or `once` (notify only on the first trigger). Ignored by security-event rules, which use per-source deduplication instead.
- **Cover type** -- Which servers the rule applies to.
- **Notification group** -- Optional. Where notifications are sent.
- **Block source IP** -- Optional (`actions` with `type: "block_source_ip"`). For `ssh_brute_force_detected` and `port_scan_detected` rules, automatically instructs targeted agents' firewalls to block the offending source IP when the rule matches.

## Supported Metric Types

### Resource Thresholds

| Rule Type | Description | `min` Threshold Meaning |
|-----------|-------------|-------------------------|
| `cpu` | CPU usage percentage | Triggers when usage >= value |
| `memory` | Memory used (bytes) | Triggers when usage >= value |
| `swap` | Swap used (bytes) | Triggers when usage >= value |
| `disk` | Disk used (bytes) | Triggers when usage >= value |
| `load1` | 1-minute load average | Triggers when load >= value |
| `load5` | 5-minute load average | Triggers when load >= value |
| `load15` | 15-minute load average | Triggers when load >= value |
| `temperature` | CPU temperature (C) | Triggers when temp >= value |
| `gpu` | GPU utilization (%) | Triggers when usage >= value |
| `tcp_conn` | TCP connections | Triggers when count >= value |
| `udp_conn` | UDP connections | Triggers when count >= value |
| `process` | Process count | Triggers when count >= value |
| `net_in_speed` | Download speed (bytes/s) | Triggers when speed >= value |
| `net_out_speed` | Upload speed (bytes/s) | Triggers when speed >= value |

### Traffic Cycle

Used to monitor cumulative traffic over a time window:

| Rule Type | Description |
|-----------|-------------|
| `transfer_in_cycle` | Inbound traffic accumulated per cycle |
| `transfer_out_cycle` | Outbound traffic accumulated per cycle |
| `transfer_all_cycle` | Combined inbound + outbound traffic per cycle |

Cycle options: `hour` / `day` / `week` / `month` / `year` / `billing` (where `billing` uses each server's configured `billing_cycle` and `billing_start_day`; note that the Web UI rule form currently omits `billing`, so configure it via the REST API).

### Network Quality

Evaluates [Network Quality Monitoring](/en/docs/monitoring#network-quality-monitoring) probe records (`network_probe_record`), not Ping tasks:

| Rule Type | Description |
|-----------|-------------|
| `network_latency` | Triggers when the maximum (`MAX`) probe latency (ms) across all probe targets over the last 10 minutes meets the threshold |
| `network_packet_loss` | Triggers when the maximum (`MAX`) probe packet loss percentage (`0`–`100`) across all probe targets over the last 10 minutes meets the threshold |

### Offline, Expiration & Events

| Rule Type | Description |
|-----------|-------------|
| `offline` | Triggers when the server has been offline for `duration` seconds |
| `expiration` | Triggers when `expired_at` is within `duration` days |
| `ip_changed` | Event-driven; triggers when the agent reports an IP change event (not part of the 60-second cycle) |
| `ssh_new_ip_login` | Event-driven; fires on a successful SSH login from a first-seen source IP (`first_seen == true`, always enforced). Supports `security.exclude_users`, `security.exclude_cidrs`, and `security.dedupe_window_seconds`. See [Security Events](/en/docs/security-events) |
| `ssh_brute_force_detected` | Event-driven; SSH brute-force burst. Supports `security.min_failed_count` and `security.dedupe_window_seconds` |
| `port_scan_detected` | Event-driven; port scan from a single source IP. Supports `security.min_distinct_ports` and `security.dedupe_window_seconds` |
| `capability_grant_detected` | Event-driven; fires when a high-risk capability (`terminal` / `exec` / `file` / `docker`) is **temporarily granted** on a server via the host-local `serverbee-agent grant` CLI. Expiry, revoke, and low-risk grants are audited but do not alert. See [Capabilities → Temporary grants](/en/docs/capabilities#temporary-grants) |

<Callout type="info">
**Settings → Alerts** provides one-click preset cards (`SecurityAlertPresets`) for creating the three security alert rules (`ssh_new_ip_login`, `ssh_brute_force_detected`, `port_scan_detected`) with sensible defaults (see [Security Events](/en/docs/security-events)). The manual rule-type dropdown does not expose those three types, so custom creation or editing outside the presets uses the Alert Rules REST API (`POST /api/alert-rules` / `PUT /api/alert-rules/{id}`).
</Callout>

The Alerts page offers a one-click **preset card** for `capability_grant_detected` ("Capability Temporarily Granted") with sensible defaults; the rule type is also selectable directly in the rule editor. It carries no `security` filter parameters and no auto-block action -- it fires on any high-risk temporary grant -- but it follows the same cover-type and maintenance-suppression behavior as the other event-driven rules.

## Threshold Configuration

Each rule item supports these fields:

```json
{
  "rule_type": "cpu",
  "min": 90.0,
  "max": null,
  "duration": null,
  "cycle_interval": null,
  "cycle_limit": null,
  "security": null
}
```

- **`min`** -- Lower threshold. When only `min` is set, the alert triggers when `value >= min`.
- **`max`** -- When only `max` is set (`min` omitted), the alert triggers when `value >= max`. When both `min` and `max` are set, `max` acts as an upper bound and the alert triggers when the value falls within `[min, max]` (`min <= value <= max`).
- **`duration`** -- Used by `offline` (seconds before triggering) and `expiration` (days threshold).
- **`cycle_interval`** -- Time window for transfer cycle rules: `hour`, `day`, `week`, `month`, `year`, or `billing`.
- **`cycle_limit`** -- Traffic limit in bytes for transfer cycle rules.
- **`security`** -- Optional `SecurityRuleParams` object used only by the three security-event rule types (ignored by metric rules):

| Parameter | Applicable Rule Types | Default | Description |
|-----------|-----------------------|---------|-------------|
| `min_failed_count` | `ssh_brute_force_detected` | `null` | Minimum failed SSH attempts required to trigger |
| `min_distinct_ports` | `port_scan_detected` | `null` | Minimum distinct probed ports required to trigger |
| `exclude_users` | `ssh_new_ip_login` | `[]` | Usernames excluded from alerting |
| `exclude_cidrs` | `ssh_new_ip_login` | `[]` | Source IP CIDR ranges excluded from alerting |
| `dedupe_window_seconds` | All 3 security rule types | `600` | Per-`(rule_id, server_id, source_ip)` notification deduplication window in seconds |

### Examples

**CPU over 90%:**
```json
{ "rule_type": "cpu", "min": 90.0 }
```

**Memory over 8 GB:**
```json
{ "rule_type": "memory", "min": 8589934592 }
```

**Server offline for more than 2 minutes:**
```json
{ "rule_type": "offline", "duration": 120 }
```

**Monthly outbound traffic over 1 TB:**
```json
{
  "rule_type": "transfer_out_cycle",
  "cycle_interval": "month",
  "cycle_limit": 1099511627776
}
```

**Server expiring within 7 days:**
```json
{ "rule_type": "expiration", "duration": 7 }
```

**SSH login from a new IP (excluding office CIDR and `deploy` user):**
```json
{
  "rule_type": "ssh_new_ip_login",
  "security": {
    "exclude_users": ["deploy"],
    "exclude_cidrs": ["203.0.113.0/24"],
    "dedupe_window_seconds": 600
  }
}
```

**Multiple conditions (AND logic):** a polling rule with several conditions triggers only when all of them hold. The following fires when CPU usage is at or above 90% *and* memory usage is at or above 8 GB:
```json
[
  { "rule_type": "cpu", "min": 90.0 },
  { "rule_type": "memory", "min": 8589934592 }
]
```

## Sampling and Trigger Logic

For resource threshold alerts (CPU, memory, disk, load, etc.), ServerBee does not trigger on a single spike:

1. The evaluator reads all raw metric records from the **last 10 minutes** (one sample per minute, so up to 10 samples).
2. It counts how many samples exceed the threshold.
3. The alert triggers only if **70% or more** of the samples exceed the threshold (at least 7 of 10).

This prevents false positives from brief, transient spikes.

For `network_latency` and `network_packet_loss` rules, ServerBee does **not** use the 70% sample model. Instead, it evaluates the single worst (`MAX`) latency or packet-loss percentage recorded across all of the server's Network Quality probe targets during the **last 10 minutes**.

## Cover Types

Each alert rule specifies which servers it applies to:

| Cover Type | Behavior |
|------------|----------|
| `all` | Applies to every server in the system |
| `include` | Applies only to the specified server IDs |
| `exclude` | Applies to all servers except the specified IDs |

## Trigger Modes and Debounce

### `always` Mode (Default)

- Sends a notification every time the condition is evaluated as true.
- **5-minute debounce** prevents notification spam: for the same (rule + server) combination, after a notification is sent, the next one is suppressed for 5 minutes even if the condition persists.

### `once` Mode

- Sends a notification only on the **first trigger**.
- No further notifications are sent until the condition recovers and triggers again.

### Security Rule Deduplication

Security-event rules (`ssh_new_ip_login`, `ssh_brute_force_detected`, `port_scan_detected`) ignore `trigger_mode` and the 5-minute polling debounce. Instead, notifications are deduplicated per `(rule_id, server_id, source_ip)` tuple using `security.dedupe_window_seconds` (default **600 seconds**).

### Renewal Expiration Reminders

For a server with a stored renewal occurrence, an expiration rule in `once` mode sends at most one reminder for each rule, server and occurrence. A new monthly deadline can therefore send its own reminder even when a 60-day window stays continuously true. Retries, Server restart and disabling automatic tracking do not resend the same occurrence.

The threshold uses the stored billing timezone's local expiry date. A zero-day reminder remains eligible throughout that date. Automatic tracking catches up to the current deadline after downtime without sending a backlog for missed occurrences. Previous automatic targets appear as **Superseded** in alert history; advancement sends no recovery notification and does not confirm provider renewal, payment or service availability. An explicitly edited date or a condition that stops matching can still produce the normal recovery transition.

Authenticated Web and native iOS views refetch the Server-owned deadline, alert history and cost advisories after catalog changes and reconnects. Clients do not calculate recurring deadlines.

### State Persistence

Trigger state is persisted to the `alert_states` table in SQLite and loaded into a hot cache on startup. As a result:

- A `once` rule that is already triggered will not re-fire after a server restart.
- Triggered-but-not-yet-recovered alerts are restored automatically after a restart.

### Recovery

When a previously triggered polling alert recovers (the condition is no longer met):

1. The alert is marked as recovered, and its state is cleared in both the in-memory cache and the database.
2. A recovery notification is dispatched to the linked notification group with `event: "resolved"`.
3. If the condition triggers again later, notifications fire according to the trigger mode.

## Maintenance Suppression

Alert notifications are suppressed while the affected server is in an active maintenance window. Rule evaluation still runs, but ServerBee skips notification delivery for that server until the window ends. Event-driven rules follow the same cover-type and maintenance suppression rules as polling-based rules.

## Blocking Source IPs

Security-event rules whose payloads carry a `source_ip` (`ssh_brute_force_detected`, `port_scan_detected`) can attach at most one `block_source_ip` action in `actions`:

```json
{
  "type": "block_source_ip",
  "cover_type": "all",
  "server_ids_json": null,
  "comment": "Auto-blocked by alert rule"
}
```

- **Target scope**: `cover_type` (`all`, `include`, or `exclude`, defaulting to `all`) and optional `server_ids_json` control which servers receive the firewall block rule, allowing an attack detected on one host to be blocked fleet-wide or on a selected subset.
- **Execution independent of notifications**: Source IP blocking runs on every matching event, even when notification delivery is suppressed by `dedupe_window_seconds` or when no notification group is attached to the rule.
- **Agent capability**: Blocking requires each target agent to report the `firewall_block` capability (`CAP_FIREWALL_BLOCK`), which is on by default and can be disabled on the agent host via `[capabilities]`; the server cannot toggle it. See [Security Events](/en/docs/security-events) and [Firewall](/en/docs/firewall).

## Notification Channels

ServerBee supports five notification channel types. Each channel is a separate entity that can be reused across multiple notification groups.

### Webhook

Send HTTP requests to any URL. Supports custom methods, headers, and body templates.

```json
{
  "url": "https://hooks.slack.com/services/xxx",
  "method": "POST",
  "headers": {
    "Content-Type": "application/json"
  },
  "body_template": "{\"text\": \"{{server_name}} {{event}}: {{message}}\"}"
}
```

If no `body_template` is provided, the default template is used. If no `Content-Type` header is set, it defaults to `application/json`.

### Telegram

Send messages to a Telegram chat via the Bot API. Messages are sent with HTML parse mode enabled.

```json
{
  "bot_token": "123456:ABC-DEF",
  "chat_id": "-1001234567890"
}
```

### Bark

Send push notifications to iOS devices via [Bark](https://github.com/Finb/Bark).

```json
{
  "server_url": "https://api.day.app",
  "device_key": "your-device-key"
}
```

### Email (via Resend)

Email notifications are delivered through [Resend](https://resend.com/). Two steps before use:

1. Set `SERVERBEE_RESEND__API_KEY` on the server (see the [Configuration](/en/docs/configuration) page).
2. Add and verify your sender domain at [resend.com/domains](https://resend.com/domains). The `from` address on each channel must belong to a verified domain.

Channel config:

```json
{
  "from": "alerts@yourdomain.com",
  "to": ["ops@example.com", "oncall@example.com"]
}
```

`to` is an array -- a single channel can deliver to multiple recipients in one API call. The subject follows the format `[ServerBee] {server_name} {event}`; the body is HTML with a plain-text fallback.

### APNs

Send direct Apple Push Notification service pushes using your own Apple Developer credentials.

```json
{
  "key_id": "ABC123DEFG",
  "team_id": "TEAM999888",
  "private_key": "-----BEGIN PRIVATE KEY-----...",
  "bundle_id": "com.example.serverbee",
  "sandbox": false
}
```

APNs requires an Apple developer key, team ID, bundle ID, and private key. Set `sandbox: true` only for development builds.

### Authenticated Mobile Alert Push (Push Relay)

Independent of manually configured `apns` notification channels, ServerBee automatically enqueues encrypted mobile alert pushes through the [Push Relay](/en/docs/push-relay) on alert rule state transitions for paired iOS installations that have mobile push enabled. You do not need to create an `apns` channel or link a notification group for paired iOS devices to receive these pushes. See [iOS Mobile Companion](/en/docs/mobile).

### Template Variables

Notification messages support the following template variables:

| Variable | Description |
|----------|-------------|
| `{{server_name}}` | Name of the affected server |
| `{{server_id}}` | Unique ID of the affected server |
| `{{rule_name}}` | Name of the triggered alert rule |
| `{{event}}` | Event type (e.g., `"triggered"`, `"resolved"`) |
| `{{message}}` | Human-readable alert message |
| `{{time}}` | Timestamp of the event (UTC) |
| `{{cpu}}` | Populated only in test notifications (`POST /api/notifications/{id}/test`); empty in live alert notifications |
| `{{memory}}` | Populated only in test notifications (`POST /api/notifications/{id}/test`); empty in live alert notifications |

The default notification template is:

```text
[ServerBee] {{server_name}} {{event}}
{{message}}
时间: {{time}}
```

Webhook, Telegram, and Bark use the default template above (`时间: {{time}}`), while Email and APNs format the timestamp line with `Time: {{time}}`.

### Testing a Channel

After creating a channel, verify its configuration with the test endpoint:

```text
POST /api/notifications/{id}/test
```

## Notification Groups

Notification channels are organized into **groups**. An alert rule is linked to a notification group, and when the rule triggers or recovers, all enabled channels in the group are dispatched.

This allows you to:

- Send the same alert to multiple channels (e.g., Telegram + Email).
- Reuse channel configurations across different alert rules.
- Enable or disable individual channels without modifying alert rules.

## Offline Detection

Offline status is determined by a dedicated background task and works together with `offline` rules:

- The task scans agent connection state every 10 seconds.
- A server is marked offline when its last report is more than 30 seconds old.
- The `offline` rule's `duration` sets how many seconds a server must stay offline before the alert fires. For example, `{ "rule_type": "offline", "duration": 60 }` triggers after 60 seconds offline.

## Example: Complete Alert Setup

Here is a typical setup for monitoring CPU usage across all servers with Telegram notifications:

1. **Create a Telegram notification channel** with your bot token and chat ID.
2. **Create a notification group** that includes the Telegram channel.
3. **Create an alert rule:**
   - Name: "High CPU Usage"
   - Rules: `[{"rule_type": "cpu", "min": 90.0}]`
   - Trigger mode: `always`
   - Cover type: `all`
   - Notification group: (the group you created)

Now, when any server's CPU stays above 90% for at least 70% of a 10-minute sampling window, you will receive a Telegram message. Subsequent notifications are debounced to once every 5 minutes while the condition persists, and a `resolved` notification is sent when CPU returns below the threshold.
